# S4-06 웹·앱 갱신 및 장시간 검증

작업 [#46](https://github.com/SongWooSeok02/pc-telemetry-forecast/issues/46). 대시보드는 [S3-08 PR #42](https://github.com/SongWooSeok02/pc-telemetry-forecast/pull/42)의 `1ab21a3`을 기준으로 빌드했다. Windows 셸은 `main`의 `455e8ea`를 개발 빌드했다. 환경은 개발 PC 1대, Windows x64 빌드 26300.9974, Node.js 26.13.0, 대시보드 0.1.0, .NET SDK 10.0.403이다. API에는 PC A/B, 지연/오류 등 재현용 응답을 사용했다. 각 재현의 실행 시각과 결과는 [실행 기록](s4-06-refresh-results.json)에 있다.

## 재현 및 기대값

각 행을 웹 브라우저와 Windows WebView2에서 각각 실행한다. 선택 확인에는 이미 등록된 서로 다른 두 PC와 새로 유입되는 센서 데이터가 필요하다. 데이터 요청은 현재값·과거·예측 비교이며 세션 확인 요청은 별도 항목으로 집계한다.

| 재현 순서 | 기대값 | 확인할 값 |
| --- | --- | --- |
| A 선택 → 과거 기간 6시간 및 확대 설정 → 페이지 스크롤 → 3→10→수동→5초 | 선택 PC, 센서, 기간, 줌, 스크롤 유지. 새 자동 주기 적용 | PC, 기간, 확대된 점 수, 스크롤 위치, 요청 시각 |
| 수동 선택 → 같은 프로필에서 새로고침 또는 앱 종료·재실행 | 저장된 수동 설정으로 시작. 초기 조회 후 사용자 동작 전까지 자동 데이터 요청 0회 | 선택값, 초기 조회 이후 시작 횟수 |
| 3초 자동 → 현재값 응답 6.5초 지연 | 지연 중 진행 작업 1개. 밀린 조회가 한꺼번에 시작되지 않음 | 지연 시간, 첫 응답까지 시작 횟수, 최대 동시 요청 |
| A의 응답을 지연 → A→B→A→B | 마지막 B만 표시. A의 데이터·오류·응답 버전은 화면에 섞이지 않음 | A 취소/늦은 응답, B 센서값·차트, 남은 요청 수 |
| 수동 → 지금 갱신 → 진행 중 최소화 → 복원 | 최소화하면 진행 요청 취소 및 이전 표시 상태 복원. 복원 자체의 데이터 조회 0회 | 창 상태, 문서/호스트 이벤트, 취소, 연결 상태, 요청 수 |
| 수동 응답 503 → 기존값과 오류 확인 → 5초 이상 대기 | 이전 값·데이터 경과·오류를 표시. 자동 재시도 0회 | 오류/경과, 다음 시작 시각 |
| 5초 자동에서 503 반복 → 정상 응답 전환 | 5→10→20→40→60초, 정상 응답 후 5초로 복귀. 기존 표시값 유지 및 증분 커서 사용 | 실패 완료·다음 시작 시각, 정상 주기, 기존값, 커서 사용 여부 |
| 자동 재시도 대기 → 수동 전환 → 대기·최소화·복원 | 재시도 예약이 해제되고 자동 데이터 시작 0회 | 선택 전후 예약과 시작 횟수 |
| 자동 최소화 → 숨김 중 10초로 변경 → 복원 | 숨김 중 데이터 요청 0회. 자동 모드 복원 즉시 조회 1회 후 새 주기로 동작 | 표시 이벤트, 숨김/복원 구간별 시작 횟수 |
| 보호 조회에서 세션 만료 401 → 재로그인 | 기존 보호 화면과 요청 해제. 로그인 후 정상 복구 | 401 코드, 화면·타이머·요청 해제, 새 세션 조회 |
| 진행 중 창 종료 | 요청 취소·가시성 바인딩 정리. 이전 창에서 새 요청을 시작하지 않음 | 종료 UTC, 잔여 요청, 호스트/렌더러 프로세스 종료 |

### 단기 재현 명령

`local-evidence/`에는 로컬 실행 로그와 테스트 도구를 둔다.

```powershell
npm --prefix dashboard install --no-package-lock
npm --prefix dashboard run build
npm --prefix dashboard run test:scheduler
npm --prefix dashboard run test:forecast
npm --prefix dashboard run test:session
npm install --prefix local-evidence/s4-06-tools --no-package-lock playwright-core@1.56.1
node dashboard/tests/refreshBrowser.mjs --edge-window
node dashboard/tests/refreshBrowser.mjs $shellExe
```

`$shellExe`는 테스트용 `PcTelemetry.Shell.exe`의 절대 경로다. 이 명령은 테스트 전용 WebView2 프로필과 루프백 주소로 셸을 띄우고 실제 Windows 창을 최소화/복원한다. `--edge-window`는 실제 탭을 전환한다. Edge 창을 띄울 수 없는 환경에서 인수 없이 실행하면 헤드리스 Edge에 문서 가시성 이벤트를 주입한다. 빠른 PC 전환 중 취소 요청 종료와 새 요청 시작의 이벤트 순서를 함께 기록한다.

### 현재 검증 결과

- 자동 검사 46개와 프로덕션 빌드 통과. 스케줄러의 72시간 가상 검사에서 작업 151,098회, 조회 타이머·진행 작업 각각 최대 1개, 종료 후 0개였다. 지연 요청 72개는 취소 상태로 끝났고 일시 실패 71회는 다시 성공했다.
- 헤드리스 Edge는 가시성 이벤트를 주입한 8개 재현을 통과했다. 창을 띄운 Edge의 자동 탭 전환에서는 문서가 `visible`로 유지돼 가시성 2개 항목의 실제 조작 확인이 남았다. WebView2는 실제 Windows 창에서 8개 중 6개 통과, 최소화·복원 2개 실패였다. 저장 복원은 같은 프로필에서 페이지 다시 읽기로 확인했다. 패키지 앱 종료·재실행은 운영 빌드에서 확인한다.
- WebView2 157.0.4341.60에서 Windows 창이 최소화됐지만 문서는 `visible`이었다. 수동 조회가 취소되지 않았고 자동 주기를 바꾸자 최소화 중 현재값 요청 1회가 시작됐다. 복원 직후에는 0회였다. 현재 셸은 컨트롤의 `Visibility`를 바꾸며 별도의 호스트 메시지 송신자가 없다. A의 호스트 가시성 전달이 연결되면 C가 실제 창에서 두 항목을 재검증한다.
- 6.5초 지연 구간의 데이터 요청은 두 클라이언트 모두 최대 1개였다. 빠른 PC 전환에서는 DevTools 요청 시작·종료 이벤트가 잠시 최대 2개로 집계됐다. 앞선 요청의 취소 또는 종료 이벤트가 다음 시작과 같은 시점에 수집됐다. 전환 후 화면에는 B 값만 표시됐다. 운영 API에서는 앞선 요청의 서버 측 종료까지 B와 확인한다.
- 4초 수집기 점검에서 JS 힙, 타이머, 데이터/인증 요청, 렌더 변경 표본을 5개 저장했다. 운영 빌드 실시간 72시간과 실제 PC·API 검증은 대기 중이다.

## 운영 빌드 72시간 측정

- **준비** — C는 S4-04의 대시보드 해시·패키지 버전과 PC/OS·Edge/WebView2·.NET 버전을 기록한다. A는 동일 대시보드를 여는 테스트 셸에서 `WindowState`, WebView2 표시 변경, `pc-telemetry:host-visibility` 송신 시각을 기록한다. B는 같은 환경의 테스트 계정과 두 PC를 연결하고, 6.5초 지연·503·세션 만료를 구간별로 재현할 수 있게 한다.
- **실행** — 같은 빌드로 웹·앱을 각각 72시간 연속 실행하며 1분마다 표본을 수집한다. 호스트 절전·재부팅·자동 갱신과 수집기 중단을 실행 기록에 남긴다. 0·24·48·72시간에 표의 주요 시나리오를 반복하고 첫 30분은 시작 및 데이터 캐시 준비 구간으로 표시한다. 세션 만료 검증 구간과 재로그인 시각을 별도 표시한다. 만료로 조회가 정지한 기간은 정상 갱신 구간과 분리해 판정한다.
- **비교** — 같은 화면·기간·주기·가시성에서 시작/중간/종료의 JS 힙과 DOM 노드, 호스트/렌더러 메모리를 비교한다. 각 24시간 구간의 중앙값·최댓값과 안정화 구간 추세를 남긴다. 프로세스 재시작과 차트에 유입된 데이터량을 따로 기록한다. 반복 시나리오 후 타이머와 진행 요청이 같은 범위로 돌아와야 하며, 정상 자동 구간에는 60초를 넘는 조회/렌더 정지를 원인과 함께 기록한다. 5초 재시도와 세션 확인은 별도 시계열로 비교한다.
- **정리** — 로그아웃 후 보호 데이터 요청과 관련 예약이 정리되는지 보고, 창을 닫아 이후 요청/렌더가 없고 테스트 프로필의 렌더러와 셸이 종료되는지 확인한다. 실행 단절·운영 오류·계속 증가하는 메모리와 요청 수는 원인과 담당, 다음 확인 시점을 남긴다.

### 측정 도구

전용 테스트 프로필의 Edge 또는 테스트 WebView2에서 DevTools 포트를 루프백에 열고, 테스트 주소 탭 하나에 로그인한다. WebView2는 시험 실행에만 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`로 포트를 전달한다. 다른 사용자가 쓰는 브라우저 프로필과 운영 계정은 사용하지 않는다.

```powershell
node dashboard/tests/observeRefresh.mjs http://127.0.0.1:9222 https://test.example local-evidence/s4-06/web-72h.jsonl
node dashboard/tests/observeRefresh.mjs http://127.0.0.1:9223 https://test.example local-evidence/s4-06/webview-72h.jsonl
```

각 명령을 독립 셸에서 실행하고 실제 테스트 origin과 로그 경로를 지정한다. 도구는 시작 시 측정 스크립트를 넣고 페이지를 한 번 다시 읽는다. 기본 259,200초·60초 간격이며 마지막 두 인수로 단기 점검 시간을 지정할 수 있다. 시작 레코드에는 관측 기간·간격·브라우저 런타임 버전과 함께 출시 빌드 대조용 비민감 번들 식별자(`bundle`, `bundleSha256`)가 기록되며, 표본 로그에는 UTC와 단조 경과, JS 힙/DOM/레이아웃, 문서 타이머의 현재·최대 수, 선택 패널 렌더 변경, 데이터와 인증의 요청/오류/취소/최대 동시 요청이 기록된다. 인증 값·본문·PC ID는 저장하지 않는다.

타이머 측정에는 문서의 `setTimeout`·`setInterval`이 포함된다. 인증과 UI 타이머를 포함하므로 가상 검사에서 얻은 조회 타이머 최대 1개는 별도 기준으로 사용한다. 렌더 지표는 선택 패널의 DOM 변경과 마지막 변경 시각이다. 보호 요청의 최대 동시 수가 높아지면 실행 로그에서 PC 변경·취소 시각을 대조한다. 테스트 프로필을 실행한 호스트·브라우저·렌더러 PID의 `WorkingSet64`와 `PrivateMemorySize64`도 `Get-Process -Id`로 1분 간격에 별도로 기록한다. 사용자 조작과 오류 주입은 아래 형식으로 남긴다.

```text
UTC | 빌드/버전 | PC/OS/런타임 | 웹/앱 | 순서·조작 | 기대값 | 실제값 | 성공/실패 | 로그·화면
```
