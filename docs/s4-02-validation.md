# S4-02 운영 배포·백업·복구

## 실행 기준

운영 구성은 Linux Docker Engine과 Compose v2를 대상으로 한다. 먼저 S3-03 집계, S3-05 예측, S2-03 장비 등록 구현이 함께 있는 리비전에 이 변경을 적용한다. 로컬 검증은 S3-05의 `9192ec1f29936e46e41a85c251cf27dfb6b3fbb0`를 사용했다. 이 리비전의 DB 마이그레이션은 001·002·004·005다. 통합 리비전이 바뀌면 그 리비전으로 마이그레이션·권한·복구 검증을 다시 실행한다.

Caddy가 공개 80/443에서 TLS를 종료하고 인증서를 발급·갱신한다. 도메인의 DNS와 방화벽을 먼저 연결한다. API, 집계, 예측, PostgreSQL에 공개 포트가 없으며 내부 네트워크로 DB에 연결한다. Caddy에서 파티션 상태 경로는 외부에 노출하지 않는다. PostgreSQL과 인증서 상태는 각각의 명명 볼륨에, 모델은 읽기 전용으로 마운트한 호스트 디렉터리에 둔다.

## 첫 배포

1. [운영 환경 예시](../infra/prod/.env.example)를 서버의 `/etc/telemetry/prod.env`로 복사한다. 빌드 리비전, DNS, 모델 및 비밀 파일의 절대 경로를 지정한다. DB 및 Caddy 이미지 ID, API 이미지 ID, PostgreSQL 버전, Compose 버전과 Git SHA를 실행 기록에 남긴다.
2. 비밀 저장소에서 관리자 비밀번호와 별도의 64자리 소문자 16진수 앱 비밀번호를 생성한다. 관리자 파일에는 관리자 비밀번호만 넣는다. 앱 파일에는 `db:5432:telemetry:telemetry_app:<앱 비밀번호>` 한 줄을 쓰고 부트스트랩 파일에는 동일한 내용을 복사한다. 모두 모드 0600으로 유지한다. 앱 파일은 컨테이너 UID 10001, 부트스트랩 파일은 대상 PostgreSQL 이미지의 `postgres` UID가 읽게 한다. 관리자 파일은 이미지 엔트리포인트의 초기 실행 사용자만 읽게 한다. UID 매핑을 사용하는 호스트는 실제 마운트 권한을 확인한다. 부트스트랩 스크립트는 PostgreSQL 엔트리포인트가 source하도록 실행 비트를 부여하지 않는다.
3. 빈 볼륨에서 DB를 먼저 띄우고 마이그레이션과 권한을 한 번 적용한다. 기존 볼륨의 재시작은 `up --wait`만 실행한다. 기존 DB를 업그레이드할 때는 백업을 확보하고 적용할 신규 마이그레이션과 권한을 별도로 검토한다. 초기 마이그레이션이 중간에 실패하면 이미 커밋된 파일을 확인한 후 재개한다.

```bash
export OPS_PROJECT=telemetry-prod OPS_ENV=/etc/telemetry/prod.env
compose=(docker compose -p "$OPS_PROJECT" --env-file "$OPS_ENV" -f infra/compose.prod.yaml)
"${compose[@]}" config --quiet
"${compose[@]}" up -d --wait db
bash infra/prod/ops.sh migrate
"${compose[@]}" up -d --build --wait
"${compose[@]}" ps
```

API와 두 작업자는 동일한 제한 DB 역할을 쓴다. 모델 활성화, 세션 발급, 원시 파티션 DDL은 관리자 경로에서 수행한다. 백업 및 복원은 Compose 호스트의 제한된 운영 계정이 수행하며, PostgreSQL 컨테이너의 로컬 소켓을 통해 관리자 작업을 실행한다. Compose 전체 설정, DB 연결 문자열, 토큰, 인증 해시, 원시 측정값은 공유 로그에 포함하지 않는다.

## 상태 감시

운영 호스트에서 chronyd를 사용한다. 호스트 스케줄러가 작업 디렉터리와 `OPS_PROJECT`, `OPS_ENV`, `OPS_TLS_HOST`, `OPS_DISK_PATH`를 명시하도록 구성한다. 다음 작업의 표준 출력과 종료 코드를 수집하고, 비정상 종료 또는 예정된 실행 누락을 팀 운영 알림에 연결한다.

| 주기 | 명령 | 감지 기준 |
|---|---|---|
| 매시간 | `bash infra/prod/ops.sh maintain` | UTC 오늘부터 3일 뒤까지 파티션 확보 후 보존 정리. 잠금 5초 또는 문장 30초 제한, SQL 오류 시 실패 |
| 매분 | `bash infra/prod/ops.sh check` | 컨테이너 가동, API와 실제 파티션 경계, 처리 가능 집계 작업 120초 초과, 예측 슬롯 2분 지연, chrony 보정 100 ms 초과 또는 비동기, TLS 인증서 검증과 만료 14일 이내, 디스크 블록·inode 사용률 85% 이상 |

DB 볼륨, 모델, 아카이브 또는 작업 디렉터리가 다른 파일시스템에 있으면 각각 같은 임계치로 호스트 감시에 추가한다. 수집된 로그에는 점검 시각, 서비스, 임계값, 종료 상태를 기록한다.

## 백업과 격리 복구

1. 모델 파일은 버전별 불변 파일로 등록한다. 모델 등록이나 파일 삭제·교체가 없는 동안 DB와 파일을 백업한다. `OPS_MODELS`는 Compose의 `TELEMETRY_MODELS`와 같은 경로로 지정한다. `OPS_SCRATCH`는 암호화된 저장소의 접근 제한 디렉터리로, `OPS_AGE_RECIPIENT`는 복구 담당자가 관리하는 age 공개키로 지정한다. 시스템에 age, GNU tar, coreutils를 설치한다.
2. `bash infra/prod/ops.sh backup /보안경로/날짜.age`를 실행한다. 스크립트는 custom-format DB 덤프와 모델 디렉터리를 하나로 암호화한다. 백업 시각과 SHA-256, 빌드, PostgreSQL 버전, 암호화 파일 크기를 접근 제한된 백업 목록에 저장한다. 별도 보관 위치로 암호화 파일을 복제하고 암호화 키는 분리 보관한다.
3. 외부에서 접근 불가능한 별도 호스트 또는 격리된 환경에 고유한 `telemetry-restore-*` 프로젝트를 만든다. 별도 DB 볼륨, 비밀값, 빈 모델 디렉터리와 별도 Compose 환경 파일을 사용한다. DB 서비스만 `up -d --wait db`로 시작한다. 복원 단계에서는 마이그레이션을 실행하지 않는다. 같은 역할 이름은 빈 DB 초기화 과정에서 생성된다.
4. 백업 목록에서 가져온 `OPS_ARCHIVE_SHA256`와 복구 담당자의 `OPS_AGE_IDENTITY` 경로를 설정한다. 격리 프로젝트와 환경 파일을 선택한 상태에서 `bash infra/prod/ops.sh restore /보안경로/날짜.age`를 실행한다. 스크립트는 인증된 암호화 파일을 열고, 빈 DB에 한 트랜잭션으로 스키마·데이터·권한을 복원한 뒤 모델을 복사한다. 모델 복사에 실패했다면 앱 시작을 보류하고 새 빈 복구 환경에서 다시 실행한다.
5. 복구 대상에서 비교가 끝날 때까지 작업자·보존 정리·외부 수집을 중단한다. 파티션 범위가 지났다면 관리자 세션에서 `SELECT ensure_measurement_partitions();`로 오늘 파티션을 먼저 확보한다. 격리 API만 `up -d --build --wait api`로 시작하고 내부에서 확인한다. 인증 및 장비 데이터는 승인된 검사 계정과 범위 안에서 조회한다. 장비, 배치·샘플 원장, 최근 측정·집계, 활성 모델 메타데이터 및 파일 SHA-256, 저장된 예측을 백업 시점의 값과 비교한다. 이후 작업자를 띄워 다음 슬롯과 대기 집계가 처리되는지 확인한다.
6. 백업 뒤 추가되거나 회수된 자격 증명은 복원 스냅샷과 운영 상태가 다를 수 있다. 운영 트래픽 연결 전에 신뢰할 수 있는 최신 회수·삭제 목록을 대조해 반영하고, 복구 검증 과정에서 공용 프록시는 계속 중단한다.

## 재현과 실측

로컬 환경은 Windows 10 x64 빌드 19045, Python 3.12.14, PostgreSQL 16.15다. PostgreSQL은 loopback에서만 열었다. 실제 운영 데이터 없이 동일 로컬 인스턴스의 두 빈 DB로 덤프와 복원을 검증했다. Docker 이미지는 이 PC에서 빌드하지 못했다.

1. PostgreSQL 16의 `pg_dump`, `pg_restore`를 PATH에 둔다. `telemetry_app` LOGIN 역할과 두 빈 `s402_verify_*` DB를 만든다. 검증 관리자와 앱 역할이 각각 접속 가능해야 한다.
2. S3-05 검증 기준 체크아웃을 `S402_SOURCE_ROOT`, `PYTHONPATH`로 지정한다. 두 DB의 관리자·앱 DSN을 각각 `S402_SOURCE_DSN`, `S402_RESTORE_DSN`, `S402_SOURCE_APP_DSN`, `S402_RESTORE_APP_DSN`에 주입한다.
3. `python infra/prod/verify_restore.py`를 실행한다. 합성 장비 등록·회수, 배치 수집, 집계 및 예측 → custom-format 덤프 → 별도 DB 복원 → 데이터·API 비교 → 중복 재전송·권한·다음 예측 슬롯 순으로 실행한다. 모델 파일은 검증 스크립트가 임시 경로에 복사한다. 운영 `age` 아카이브 흐름은 아래 서버 점검 항목에 포함한다.

## 운영 서버 확인 항목

- [ ] Compose 이미지 빌드 및 최초 배포, 공개 TLS 발급·만료·호스트명 검증, chrony 오프셋, 디스크·inode 사용률, 외부 경보 전달을 기록한다.
- [ ] 합성 환경에서 Compose 재시작 후 볼륨 영속성을 확인한다. DB 중단 중 API 수집 실패와 재시작 후 정상 응답을 확인한다. 작업자를 중단한 동안 적체 및 오래된 슬롯이 탐지되고 재가동 후 정상화되는지 기록한다.
- [ ] 실제 서버에서 암호화 백업을 만들고 격리 Compose 환경으로 복원한다. 복원 전후 비교와 중복 수집·회수·모델 재개 결과를 기록한다.
