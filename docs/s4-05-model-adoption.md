# S4-05 모델 비교와 새 48시간 재평가

작업 카드 [#41](https://github.com/SongWooSeok02/pc-telemetry-forecast/issues/41). 온도 모델 PR #37의 모델 JSON과 평가 함수를 사용합니다. PC·CPU/GPU 대상별로 따로 실행합니다.

## 11월 21일 기준 출시 판정 (기록)

| 완료 조건 | 실제 확인 결과 | 상태 |

| 11/21 09:00까지 고정 | 실제 모델·개발 보고서와 고정 기록이 없음 | 미완료 |

현재 출시 경로는 기준 모델입니다. 검증된 개발 기준이 있으면 그 기준을 쓰고, 없으면 현재 온도 유지 모델을 지원 대상마다 생성합니다. 이 기록으로 실측 학습 모델을 채택하거나 배포하지 않았습니다.

## 평가 일정과 수집

평가 설정의 해시를 남기고 고정 이후에만 데이터를 수집합니다. 2026-11-27 소유자 요청에 따라 일정은 도구에 넣지 않고 `freeze`에 넘깁니다. 기존 11/21 고정·11/23 보고 일정은 지났으므로 사용하지 않습니다. 새 일정 날짜는 아직 합의 기록이 없습니다. 합의된 고정 상한과 보고 마감을 기록한 뒤 그 값으로 실행합니다.

구간은 보고 마감 `R`에서 계산합니다. 입력 시각에는 시간대가 필요합니다. 두 마감과 구간 경계는 UTC로 계산해 manifest에 기록합니다. UTC로 바꾼 마감에 소수 초가 남으면 구간이 초별 수집 격자에서 벗어나므로 `freeze`와 manifest 재검사에서 거부합니다.

| 구간 | 시작 | 종료 (미포함) | 용도 |
|---|---|---|---|
| 선행 입력 여유 | R − 48시간 7분 | R − 48시간 2분 | 경계용 별도 확보 |
| 48시간 본구간 | R − 48시간 2분 | R − 2분 | 최종 평가 |
| 후행 정답 여유 | R − 2분 | R − 1분 | 경계용 별도 확보 |
| 결과 기록 | R − 1분 | R | 산출물 생성과 제출 |

고정 상한 `--freeze-deadline`은 후행 정답 여유 종료(R − 1분)보다 앞서야 합니다. 두 마감과 계산된 구간은 manifest의 `policy`에 들어가 해시로 묶입니다. `evaluate`는 manifest의 일정만 사용합니다. 일정 값을 고치거나 일정이 없는 이전 manifest를 넣으면 `freeze mismatch`로 멈춥니다. 보고 마감 시각까지 평가하면 정시 평가입니다. 1초라도 늦으면 `report_deadline_missed`로 기준 모델을 내보냅니다. 마감은 게시 직전 마지막 검사의 판정 시각에 적용됩니다. 그 뒤 보고서·출시 모델 파일 기록은 마감 안 완료를 보장하지 않습니다. 소유자 요청은 "보고 마감"만 말하고 파일 기록 완료 시점은 정하지 않았습니다. 따라서 기존 동작을 유지합니다. 마감 안 파일 완료가 필요하면 팀이 요구를 정해야 합니다.

고정 상한이 선행 수집 시작보다 늦어도 채택하려면 선행 수집이 시작되는 R − 48시간 7분까지 고정과 독립 기록을 끝내야 합니다. 본구간은 48시간으로 고정하고, 입력 300초와 +60초 정답이 모두 본구간에 들어오는 표본만 점수에 사용합니다. 경계용 데이터는 확보 여부를 별도로 검증합니다. 1분은 실행 시간 보장이 아니며, 수집 내보내기나 평가가 늦어지면 기준 모델로 판정합니다.

각 PC에서 본구간의 두 24시간 구간마다 완료 시나리오를 2회 이상 확보합니다. 4세션과 전체 전환 16회는 최소 계획이고 CPU·GPU 각각 8회여서 대상별 10회 기준을 충족하지 못합니다. 실제 계획은 2회와 3회로 나눈 최소 5세션·전체 전환 20회입니다. 중단·품질 제외 시 보충합니다. 유효 전환은 S1-09의 해당 장비·대상에서 검토된 경계이며, 해당 시각의 입력·정답 품질까지 확인합니다. 초별 표본을 독립 전환으로 세지 않습니다.

## 실행과 제출

1. C가 11/19~20 개발 결과와 검증 기준 선택을 확인한 뒤, 마지막으로 튜닝에서 사용한 원천 관측·라벨 시각까지 포함하는 종료 경계를 UTC로 기록합니다. 개발 보고서의 분할 종료, 실제 관측·라벨 마지막 시각이 기록 범위 안에 들어야 합니다.
2. CSV를 열기 전에 고정 명령을 실행합니다. 모델 파일, S3-04 개발 보고서, 파이프라인 소스, 고정 특징·전처리·품질·평가 설정을 해시로 묶습니다. 팀원이 고정 manifest 해시와 기록 시각을 확인할 수 있는 저장소나 변경 이력에 남깁니다. CLI 로컬 시각이나 참조 문자열만으로는 수집 독립성을 증명할 수 없습니다.
3. 별도 보관한 새 데이터와 라벨을 평가합니다. 팀원이 고정 기록·시각, 48시간 CSV/라벨의 수집 일자, 튜닝 미사용 여부를 대조하고 확인한 manifest 해시를 입력합니다. 파일 해시가 달라졌다는 사실만으로 데이터 독립성을 인정하지 않습니다.
4. 결과 JSON에서 모델 SHA-256, 기간·라벨, 전체·유휴·고부하·전환 MAE와 결측률, 채택 또는 기각 이유를 확인합니다. 전체 MAE 10% 이상 개선과 고부하·전환 악화 각각 5% 이내를 함께 적용합니다. 기준 MAE가 0.1°C 미만이거나 일정·품질·전환·성능 미달이면 기준 모델을 내보냅니다. JSON 보고서와 출시 모델을 새 파일에 저장한 뒤 S4-07·S5-06/07에 해시와 함께 전달합니다.
5. 모델·특징·전처리·평가 설정을 바꿀 필요가 있으면 이 고정과 해당 홀드아웃의 채택 결과를 폐기합니다. 기존 구간은 개발 자료로만 취급하고 새 일정과 새 48시간을 확보합니다. 일정 변경은 합의 기록을 남기고 새 `freeze`로 고정합니다.

출력 폴더를 만든 뒤 PC/대상마다 실행합니다. 아래 값은 입력 자리표시자입니다. 마감 값은 `2026-12-01T09:00+09:00`처럼 시간대를 붙인 ISO 형식이며, 이 예시는 형식일 뿐 합의 날짜가 아닙니다.

```powershell
python -m ml.final_evaluation freeze --model model.json --development-report evaluation.json --reviewed-through <UTC_END> --freeze-deadline <AGREED_FREEZE_DEADLINE> --report-deadline <AGREED_REPORT_DEADLINE> --output freeze.json
python -m ml.final_evaluation evaluate --model model.json --freeze freeze.json --input fresh.csv --labels fresh-labels.json --expected-freeze-sha256 <RECORDED_SHA256> --freeze-evidence <REVIEWABLE_RECORD> --output final-report.json --release-output release-model.json
python -m ml.temperature_model predict --input latest.csv --artifact release-model.json
```

검증된 고정 모델이 없는 PC/대상에는 아래 명령을 사용합니다.

```powershell
python -m ml.final_evaluation baseline-release --machine-id <PC_ID> --target cpu --output release-model.json
```

`evaluate`는 보고서와 출시 모델을 한 쌍으로만 게시합니다. 두 내용을 먼저 완전히 직렬화하고 같은 폴더의 임시 파일에 기록·동기화한 뒤, 기존 파일을 덮어쓰지 않는 링크로 보고서→출시 모델 순서로 게시합니다. 어느 단계든 실패하면 이번 실행이 게시한 파일과 임시 파일을 지우므로 보고서만 남아 다음 실행을 막지 않으며, 같은 경로로 다시 실행하면 됩니다. 출시 모델의 `s4_05.evaluation_report_sha256`은 함께 만든 보고서 바이트의 SHA-256이며, `release_matches_report()`로 쌍을 확인한 출시 모델만 S4-07·S5에 전달합니다. 프로세스가 강제 종료되어 출시 모델 없이 보고서만 남은 경우 다음 실행은 `incomplete previous run`으로 멈춥니다. 이 보고서는 정상 결과가 아니므로 내용을 보존·확인한 뒤 삭제하고 다시 실행합니다. 보고서 없이 남은 출시 모델은 `orphaned release`로 멈추며, 이런 출시 모델이나 해시가 맞지 않는 출시 모델은 배포하지 않고 확인 후 삭제합니다. 출력 경로 검사는 `Path.exists()` 대신 `os.path.lexists()`를 사용해 대상이 사라진 심볼릭 링크도 사용 중인 경로로 보고하고, 어떤 종류(파일·심볼릭 링크·대상 없는 심볼릭 링크)가 경로를 차지하는지 오류에 표시합니다.

실측 원본과 장비별 모델/결과는 접근이 제한된 위치에 보관합니다. 조기 실행은 점수를 공개하지 않습니다. 고정 해시 불일치나 입력 규격 오류는 실패로 종료되며 해당 후보를 사용하지 않습니다.

## 검증과 담당

재현 명령과 실행 환경·실행 시각·예상값·실제값은 [검증 기록](s4-05-validation.json)에 있습니다. 48시간 합성 통합 검사는 2회/3회 세션, 유효 전환 10회, 기준 MAE 20°C, 후보 MAE 10°C, 결측률 0에서 채택을 재현합니다. 이 수치는 판정 경로를 확인하기 위한 고정 테스트 입력입니다. 설정한 새 일정의 정시 평가와 마감 1초 초과, 일정 변조·누락 manifest 거부, 일정 미달, 조기 조회, 입력 재사용, 모델/평가 코드 변경에서 채택이 막히는 것도 검사합니다. 출시 모델 게시 실패 시 보고서까지 되돌려 반쪽 결과가 남지 않고 재실행되는지, 직렬화 불가 값·임시 파일 기록 실패·기존 파일·보고서만 남은 이전 실행도 검사합니다.

차단 원인은 실제 수집 자료와 당시 개발·고정 증거 부재입니다. C는 S1-09 수집 담당 및 S3-04 모델 담당과 자료·장비별 계획을 확인하고, 다음 확인 시점은 새 일정 합의 후 선행 수집 시작 이전입니다. 미확보 시 기준 모델 경로를 S4-07·S5 담당과 확인합니다. 실제 48시간 평가·팀원 검토·CI가 완료될 때까지 #41은 열어 둡니다.
