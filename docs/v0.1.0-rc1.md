# v0.1.0-rc1 릴리스 노트

2026-11-20 KST 기준 **배포 보류**. 기능 고정 및 RC 판정은 2026-11-24 KST에 B(@SongWooSeok02)가 A·C의 검증 결과를 모아 기록한다. 아래 재검증 일정은 팀 확인 전 제안이다.

## 기능 범위

Windows x64 수집·버퍼·재전송, 웹·WebView2의 현재값·이력·온도 예측, 수동/자동 갱신, Linux 운영 서버의 수집·보존·백업·복구를 후보 범위로 둔다. S4-05 채택 근거가 확보되기 전 온도 예측은 `builtin:persistence:v1`로 고정하는 안을 적용한다. 예측 불가는 `builtin:none`으로 기록한다. 학습 모델 활성화와 실험 전력 예측은 후보 범위에서 제외한다.

## 동일 리비전에서 패키지 준비

1. B가 A·C의 선행 변경과 필요한 CI를 대조한 뒤 깨끗한 통합 체크아웃의 전체 Git SHA를 기록한다. A는 해당 체크아웃의 Windows 개발 환경에서 팀이 승인한 코드 서명 인증서와 타임스탬프 URL로 빌드한다. 출력은 새 디렉터리로 지정한다.

   ```powershell
   $out = Join-Path $env:TEMP 'pc-telemetry-v0.1.0-rc1-win-x64'
   .\desktop\windows\install\Publish-PcTelemetry.ps1 -ReleaseCandidate -Out $out `
       -SigningCertificate $approvedCertificate -TimestampServer $approvedTimestampUrl
   ```

   스크립트가 빌드 버전, 서명 후 파일별 SHA-256 및 서명 인증서 지문을 `manifest.json`에 기록한다. 설치 스크립트가 루트에 있도록 전체 폴더 내용을 ZIP으로 묶고 최종 ZIP의 SHA-256을 기록한다. 새 Windows PC에서 ZIP의 SHA-256을 먼저 대조한 뒤 압축을 풀어 매니페스트에 있는 모든 파일의 SHA-256, `signed_paths`의 Authenticode 상태·게시자·타임스탬프, 제품 버전, WebView2 부트스트래퍼의 Microsoft 서명을 확인한다. 검증이 끝난 ZIP을 그대로 배포한다. [설치 절차](../desktop/windows/README.md)
2. B는 같은 SHA의 서버 소스·마이그레이션·운영 설정과 웹 빌드를 고정한다. `TELEMETRY_REVISION=v0.1.0-rc1`로 서버 예행연습을 수행하고 실제 사용한 백엔드·PostgreSQL·Caddy 이미지의 레지스트리 다이제스트를 기록한다. 배포용 Compose 오버라이드에서 API·집계·예측에 같은 백엔드 다이제스트를 지정하고 DB·프록시도 기록한 다이제스트로 고정한다. 새 서버에서 고정 이미지로 `docker compose up --no-build -d --wait`를 실행한다. 운영 경로와 비밀은 서버에서 주입한다. 소스/구성 묶음과 웹 배포물의 SHA-256 및 이미지 다이제스트를 설치 ZIP SHA-256과 함께 기록한다. [운영 배포 및 복구](s4-02-validation.md)
3. 모델 버전, 활성 대상, 입력 규격, 평가 보고서, 파일을 쓰는 모델의 SHA-256을 기록한다. 내장 기준 모델은 외부 모델 파일 없이 서버 이미지 다이제스트로 구현을 식별한다. 테스트 대상의 활성 모델을 확인하고 유효한 입력을 넣어 예측 응답의 `model_version`을 비교한다. [모델 전환·조회 계약](s3-05-forecast.md)
4. 배포 전 기존 Windows 설치본과 서버 이미지·설정·모델 및 암호화 DB 백업을 확보한다. 새 PC와 격리 서버에서 신규 설치 → 이전 버전에서 업데이트 → 이전 배포물로 롤백을 검증한다. DB 스키마가 이전 이미지와 호환되는지 확인하고, 복원이 필요한 경우 격리 환경에서 백업·모델 복구와 회수된 자격 증명 재대조를 마친 뒤 전환한다. 롤백 시 백업 이후 유입 데이터의 보존 범위도 기록한다.
