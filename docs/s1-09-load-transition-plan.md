# S1-09 부하 전환 수집 계획과 라벨 규격

상태: **절차·라벨 초안 준비 / 실제 PC 수집 미실행**. `docs/sensor-support.md`는 실제 PC의 센서 지원이 아직 미관측이라고 기록한다. 따라서 이 문서와 빈 인덱스는 측정 결과나 수집 완료 증거가 아니다.

작업 카드: [S1-09 #13](https://github.com/SongWooSeok02/pc-telemetry-forecast/issues/13). 라벨 JSON Schema는 `docs/s1-09-label.schema.json`, 수집 목록은 `docs/s1-09-collection-index.csv`다. 이는 S1-01 telemetry 계약 초안의 필드를 변경하지 않는 별도 sidecar 초안이다.

## 1. 고정 시나리오

각 PC에서 아래 5개 구간을 순서대로 수행한다. 구간 길이는 계획값이며 UTC 시작·종료 시각과 실제 센서 관측으로 실제 경과를 남긴다.

| 순서 | 단계 ID | 작업 라벨 | 부하 대상 | 계획 길이 | 전환 이벤트 |
|---:|---|---|---|---:|---|
| 1 | `idle` | 유휴 기준 | 없음 | 10분 | — |
| 2 | `cpu_load` | CPU 부하 | CPU | 10분 | 유휴 → CPU 부하 |
| 3 | `cpu_cooldown` | CPU 후 냉각 | 없음 | 10분 | CPU 부하 → 냉각 |
| 4 | `gpu_load` | GPU 부하 | GPU | 10분 | 냉각 → GPU 부하 |
| 5 | `gpu_cooldown` | GPU 후 냉각 | 없음 | 10분 | GPU 부하 → 냉각 |

한 세션은 50분이며 독립 전환 이벤트는 정확히 4개다. 초당 측정 행 수, 센서 수, 각 부하 구간 안의 반복 샘플 수를 독립 전환 수로 세지 않는다. 세션마다 새 `session_id`와 전환마다 새 `transition_id`를 발급한다. 다음 세션은 새 유휴 기준 구간에서 시작하고 이전 부하 구간과 시간상 겹치면 안 된다.

## 2. 라벨 기록 규칙

- 시각은 UTC RFC 3339 `YYYY-MM-DDTHH:mm:ss.ffffffZ`로 기록한다. 단계 시작·종료 시각은 라벨러의 벽시계 구간이고, 측정 원본의 `observed_at`은 수정하지 않는다.
- 각 전환은 `transition_id`, 출발/도착 단계, CPU/GPU 대상, 관측 여부와 도착 단계 시작 UTC로 기록한다. 중단되어 전환이 발생하지 않았으면 `not_observed`와 null 시각을 남긴다.
- 라벨은 원시 telemetry와 별도 sidecar로 저장하고 `machine_id`, `boot_session_id`, `sensor_config_id`, 에이전트 빌드와 세션/단계 구간으로 연결한다. 현재 수집 payload에 작업 라벨을 임의로 추가하지 않는다.
- 장비는 `PC-A` 같은 별칭으로 표시한다. 저장소나 PR에 호스트명, 사용자명, 일련번호, IP, 인증 토큰, 원시 텔레메트리를 넣지 않는다.
- 부품별 실제 모델, OS 빌드, 에이전트 버전/커밋, 센서 ID·단위·품질, 센서 구성 ID를 기록한다. 지원 여부를 확인하지 못한 센서는 `unobserved`로 두며 `unsupported`나 0으로 바꾸지 않는다.
- 팬은 각 단계의 제어 모드(`auto`, `fixed`, `unknown`), 요청 설정(있으면 %), 관측된 RPM 센서 ID/품질을 기록한다. 시나리오 수행을 위해 자동 팬 제어를 추가하거나 변경하지 않는다.
- 부하 도구 이름·정확한 버전·프로파일을 CPU/GPU 부하 단계에 기록한다. 같은 시나리오를 재현할 수 있도록 설정 식별자를 남기되 개인 경로나 비밀 값은 저장하지 않는다.
- 완료/중단 여부와 중단 사유를 필수로 기록한다. 예정 시간과 실제 시간이 다르면 실제 시각을 보존하고 사유를 남긴다.
- 세션은 `completed` 또는 `aborted`로 기록한다. 중단된 세션도 5단계 배열을 유지하고 실행 전 단계는 `not_started`와 null 시작/종료 시각으로 표시한다. 실행을 시작한 단계는 실제 시작·종료 시각을 기록한다.

규격은 `s1-09-label-v0.1-draft`다. 다른 작업과의 계약 합의 전까지 분석용 제안으로 취급한다.

## 3. 안전 사전 점검과 중단 기준

부하를 시작하기 전에 CPU/GPU 모델별 제조사 온도 한계와 출처를 확인하고, 그 한계보다 낮은 보수적인 중단 임계값을 정해 라벨에 기록한다. 모델이나 한계를 확인할 수 없으면 부하 단계를 실행하지 않는다. 고정된 보편 온도값을 임의로 쓰지 않는다.

다음 중 하나면 현재 부하를 즉시 종료하고 냉각/관찰 상태로 전환한다. 종료 후에도 온도 또는 오류 상태가 안전하지 않으면 장비를 정상 종료할지 담당자가 판단하고, 세션을 중단한다.

1. CPU 또는 GPU 온도가 기록된 중단 임계값에 도달한다.
2. 온도 센서가 `missing`, `error`, `unsupported`로 바뀌거나 센서/에이전트 수집 오류가 발생한다.
3. 장비가 불안정해지거나 운영자/장비 사용자가 중단을 요청한다.

중단 시점, 당시 단계, 대상 센서, 사유 코드, 마지막 정상 관측 시각을 기록한다. 안전 기준이 불명확한 경우 실측 실행을 미루고 담당자에게 확인한다. 이 문서의 작성만으로 물리 장비 부하를 실행하거나 팬 설정을 바꾸지 않는다.

## 4. 수집 일정과 전환 수 산정

### 초기 수집

센서 지원과 안전 한계를 확인한 PC부터 첫 주에 PC별 하루 1회 이상 실행한다. 실제 가용 장비와 담당자, 가능한 시간대가 확정되기 전에는 일정표를 완료로 표시하지 않는다. 현재 날짜는 카드의 계획 기간(2026-11-03 종료) 이후이며, 실제 PC 접근/관측 기록은 `docs/sensor-support.md`에 아직 없다. 담당자와 새 시작일을 정해야 한다.

### 최종 테스트·재평가

카드의 기준은 48시간 동안 시나리오 4회, 전환 16회이며 PC별 하루 2회 이상이다. 그러나 CPU와 GPU를 각각 하나의 “대상”으로 계산하면 한 시나리오에 CPU 전환 2회, GPU 전환 2회가 있어 4회 실행은 CPU 8회·GPU 8회만 만든다. 이는 PC·대상별 유효 독립 전환 10회 조건에 미달한다.

| 48시간 계획 | 세션 수 | 전체 전환 | CPU 대상 전환 | GPU 대상 전환 | 대상별 10회 충족 |
|---|---:|---:|---:|---:|---|
| 카드의 기준 계획 | 4 | 16 | 8 | 8 | 아니오 |
| CPU/GPU별 10회를 맞추는 최소 계획 제안 | 5 | 20 | 10 | 10 | 예, 유효 전환이 모두 남는 경우 |

5회 제안은 48시간에 2회/3회로 배치한다. 중단·결측·품질 제외가 있으면 유효 수는 줄어든다. 만약 “대상별”이 CPU/GPU가 아니라 네 가지 정확한 경계 각각을 뜻한다면 10회씩 확보하려면 10개 세션, 40개 전환이 필요하다. 이 해석 차이와 4회/16회 대 10회 완료 조건은 카드 담당자가 정정/승인하기 전까지 완료로 판정하지 않는다. 필요한 유효 수를 충족하지 못하면 최종 48시간 구간을 연장하고 실제 종료 시각을 기록한다.

## 5. 운영 체크와 수집 인덱스

세션 전:

1. 실제 `machine_id`, CPU/GPU 모델, 에이전트 빌드, `sensor_config_id`와 대상 센서 ID를 확인한다.
2. 제조사 한계 출처와 중단 임계값을 기록한다. 온도 한계가 미확인인 PC는 부하 테스트 대상에서 제외한다.
3. 시각 동기화·수집 서비스·디스크 여유·팬 설정을 확인하고 세션 ID를 발급한다.
4. 원본 telemetry를 정상적으로 수집하는지 확인한 뒤 5단계를 수행한다.

세션 후:

1. 각 단계 경계와 최종 상태를 라벨링하고 telemetry 누락/센서 오류/중단 사유를 확인한다.
2. sidecar 및 정제된 결과의 SHA-256을 기록하고 접근 제한된 저장소에 원본을 보관한다.
3. `docs/s1-09-collection-index.csv`에 정제된 세션 인덱스만 추가한다. 아직 수집하지 않은 행이나 합성 수치는 추가하지 않는다.
4. PC별·CPU/GPU별·전환 종류별 계획/완료/중단/결측/유효 독립 전환 수를 집계한다. 사후 품질 검토자는 각 관측 전환을 `pending`, `valid`, `excluded`로 판정하고 제외 사유를 남긴다. `pending`, `excluded`, `not_observed`는 유효 전환 수에 포함하지 않는다.

## 6. 현재 증거와 남은 일

- [S1-07 실제 PC 센서 지원표](sensor-support.md): 실제 PC 2대의 센서값은 미관측으로 기록되어 있다.
- [S1-01 telemetry 계약](../contracts/README.md): 공동 검토 대기 중이다. 이 초안은 계약을 확정하거나 변경하지 않는다.
- 현재 상태: 실측 세션 0건으로 취급하며, 실제 수집 성공/실패·온도 분포·센서 품질 수치를 주장하지 않는다.
- 다음 단계: 담당자가 PC 접근, 모델별 안전 한계, 부하 도구/버전, 일정, 10회 목표의 집계 단위를 확정한 뒤 현장 실행과 독립 검토를 수행한다.
