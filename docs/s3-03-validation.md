# S3-03 사용자별 조회·집계·보존

장비, 원시 측정, 집계, 예측은 S2-03의 사용자 Bearer 세션과 S2-04 소유권으로 제한한다.
미소유·삭제 장비는 404, 사용자 세션이 없거나 장비 토큰만 있으면 401이다.
`GET /v1/machines/{machine_id}/{measurements|aggregates|predictions}`는 `sensor_id`,
시간대가 포함된 `start`/`end`의 반개구간, 선택적인 `limit`을 받는다. `aggregates`는
`bucket_seconds=10|60`(기본 60)을 받고, `predictions`는 `target_at`으로 조회한다.
예측 생성은 S3-05가 담당한다. 집계의 `pending`, `updated_at`, `provisional`은 분리되어 있어
아직 게시되지 않은 값과 재집계 중인 이전 값을 구분할 수 있다.

S2-05 [차트 PR #17](https://github.com/SongWooSeok02/pc-telemetry-forecast/pull/17)의
`GET /v1/dashboard/machines/{machine_id}/sensors/{sensor_id}/history` 계약을 제공한다.
최초에는 `from`, `to`, `resolution`(raw/10s/1m/5m/1h), 이후에는 `cursor`만 보낸다.
5분·1시간은 1분 행의 유효 개수로 가중 평균한다. PostgreSQL 가시성 스냅샷을 커서에 포함해,
조회 당시 미커밋이던 수집·재집계 트랜잭션도 다음 요청에서 변경으로 감지한다.
커서는 권한 증명이 아니므로 재요청마다 세션과 장비 소유권을 검사한다. 단위는 카탈로그 값
(예: `Cel`)이다. #17의 브라우저 호출에 사용자 세션 전달 및 카탈로그 매핑을 연결해야 한다.

## 운영

- 기존 DB에는 `004_aggregation.sql`만 추가 적용한다. [#27](https://github.com/SongWooSeok02/pc-telemetry-forecast/pull/27)의
  `003_quality.sql`은 별도다. S3-03은 미병합 에이전트 변경을 포함하지 않는다.
- `python -m backend.aggregation`을 상시 실행한다. API DB 역할에 새 집계·예측 테이블의
  SELECT를 추가한다. 작업자에는 측정 SELECT, 큐 SELECT/UPDATE/DELETE, 집계 SELECT/INSERT/UPDATE를 부여한다.
  마이그레이션 소유자로 `python -m backend.partitions`를 매시간 실행하고 실패를 알린다.
  `reaggregation_queue`의 대기량, 가장 오래된 `ready_at`, 재시도 및 작업자 오류 로그를 감시한다.
- UTC 관측 구간 시작 기준 10초 집계 30일, 1분 집계 90일을 적용한다. 최근 24시간과
  재집계 대기 버킷은 미확정이다. 24시간보다 오래된 관측도 수집이 성공하면 큐에 넣는다.
  관측 시간이 보존 범위 밖이면 큐는 처리하되 만료된 집계를 다시 게시하지 않는다.
- 원시 조회는 `received_at` 7일로 제한한다. 물리 삭제는 UTC 일별 파티션의 **끝**이
  7일 경계를 지난 뒤 수행하며, 그 파티션에 의존하는 대기 작업이 있으면 삭제를 미룬다.
  유지보수 잠금은 수집 및 작업자의 원시 읽기와 경합하므로 잠금 제한 및 S4-03 부하 검증이 필요하다.
- 이미 삭제된 원시 행이 있는 버킷에 뒤늦게 새 행이 들어오면 남아 있는 원시 행만으로 재계산한다.
  삭제한 표본까지 포함한 과거 집계를 보존해야 한다면 지연 수락 범위나 별도 장기 보관 정책에
  합의해야 한다. 현재 수집 계약의 관측 시각 수락 범위는 그대로다.

## 검증 및 자체 리뷰

- 빌드: 원격 main `455e8ea` 기반 S3-03 PR. Windows 10 22H2 (19045), 로컬 개발 PC,
  Python 3.12.16, PostgreSQL 16.15, DB 세션 Asia/Seoul, 합성 PC/장비 토큰.
- 재현: 격리 테스트 DB의 `TEST_DATABASE_URL`을 지정하고
  `python -m unittest discover -s tests -p 'test_*.py'`, 이어서
  `python -m ruff check --select E9,F63,F7,F82 backend tests`, `git diff --check`.
  CI에서도 `test_aggregation.py`를 실행한다.
- 실행 결과 (2026-11-16 03:30 KST): 53건 성공, 0건 실패·건너뜀 (22.438초).
  Ruff 및 Git 공백 검사도 통과했다.
- 해당 장비의 25시간 전 구간에 40, 60, 80, 20과 결측 1건을 수신했다. 10초 결과는
  40/60/3, 다음 10초는 80/80/1, 1분 평균과 유효 수는 50/4로 기대와 일치했다.
  작업자가 읽은 뒤 60이 도착했을 때 이전 세대는 게시되지 않았다. 25시간 구간은 처리 후
  확정, 현재 구간은 미확정이었다. 타 사용자 404, 장비 토큰 401, 삭제 장비 404였다.
- 실패를 유도했을 때 큐가 남고 재시도 횟수가 1로 증가했다. 대기 중인 9일 전 수신
  파티션은 보존되었고, 작업자의 원시 읽기가 열린 동안 삭제 잠금은 실패했다. 재시도 성공 후
  파티션을 삭제하고 집계값 40을 확인했다. 31일에는 1분만, 91일에는 두 해상도 모두 만료됐다.
- 5분 차트가 40, 90, 100의 가중 평균 230/3을 반환했다. 커서 이후 변경이 없으면
  빈 목록이었고, 늦은 값 10이 수신되면 원시 변경과 집계 대기가 보였다. 처리 후 같은
  5분 구간의 평균 60, 최대 100, 유효수 4를 다시 반환했다.
- 자체 리뷰에서 커밋 경합, 재시도 롤백, 소유권 및 커서 재사용, 원시 삭제와 과거 보존의
  차이를 확인했다. 실제 브라우저 로그인·차트 통합, S4-03의 실규모 검증, 팀원 리뷰는 남아 있다.
